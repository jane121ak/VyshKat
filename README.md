# ВышКат — учёт парка техники

Консольное приложение для домашнего задания № 1 по конструированию программного обеспечения (ВШЭ). Проект демонстрирует небольшую объектную модель транспорта и вещей, применение SOLID, DI-контейнера и поведенческих юнит-тестов.

## Как запустить

Нужен **.NET SDK 10.0** (проекты используют `net10.0`). Команды выполняются из корня, где находится `VyshKat.slnx`.

```bash
dotnet restore VyshKat.slnx
dotnet build VyshKat.slnx
dotnet test VyshKat.slnx
dotnet run --project VyshKat/VyshKat.csproj
```

По умолчанию запускается **готовая демонстрация**. Для добавления собственных устройств через меню:

```bash
dotnet run --project VyshKat/VyshKat.csproj -- --interactive
```

В интерактивном режиме можно принять транспорт, добавить вещь на баланс и вывести отчёты. Все данные хранятся только в памяти: сохранение в файл или БД по условию задания не требуется.

Для сбора покрытия (пакет `coverlet.collector` указан в тестовом проекте):

```bash
dotnet test VyshKat.slnx --collect:"XPlat Code Coverage"
```

Отчёт `coverage.cobertura.xml` появится в `VyshKat.Tests/TestResults/`. Фактический процент покрытия нужно смотреть после запуска тестов; не следует считать 60% достигнутыми без измерения.

## Структура

- `VyshKat.Domain/Interfaces/` — контракт инвентаризируемого объекта (`IInventoryItem`), транспорта (`ITransport`), вещи (`IThing`), потребителя энергии (`IPowerConsumer`) и техосмотра (`IServiceCenter`).
- `VyshKat.Domain/Transports/` — `TransportBase`, `Scooter`, `Bike`, `ElectricBike`.
- `VyshKat.Domain/Things/` — `ThingBase`, `Helmet`, `ChargingStation`.
- `VyshKat.Services/ServiceCenter.cs` — упрощённый техосмотр.
- `VyshKat.Services/FleetManager.cs` — приёмка, инвентарный учёт и отчёты.
- `VyshKat/Program.cs` — настройка DI, демонстрация и консольное меню.
- `VyshKat.Tests/` — тесты моделей, `FleetManager`, `ServiceCenter`, подмена техосмотра через `FakeServiceCenter`.

## Логика решения

### Приёмка техники и правило для новичков

`FleetManager.TryAddTransport` сначала проверяет уникальность инвентарного номера, затем вызывает `IServiceCenter.Inspect`. При отказе транспорт **не попадает на баланс**, поэтому не учитывается в количестве, энергопотреблении и списке для новичков.

В этой учебной реализации техосмотр `ServiceCenter` опирается на свойство `ITransport.IsServiceable` (исправен / неисправен). Это упрощение: в реальном сервисе потребовалась бы диагностика. **Простота управления не определяет исправность.** Отдельный отчёт `GetBeginnerFriendlyTransports` показывает только уже принятый транспорт с `BeginnerSimplicity >= 6` (допустимый диапазон 1–10).

### Инвентаризация и энергия

На баланс попадают **транспорт и вещи**, но не сотрудники. Все объекты имеют имя и инвентарный номер благодаря `IInventoryItem`. Номера уникальны среди всех объектов, при сравнении не учитывается регистр. Пустые названия/номера, некорректная простота управления и отрицательная, бесконечная либо `NaN` энергия запрещены.

`FleetManager.GetTotalDailyEnergyConsumption` суммирует суточное энергопотребление объектов, реализующих `IPowerConsumer`: электросамокатов, электровелосипедов **и зарядных станций**, но не обычных велосипедов и шлемов. `GetAllItems` возвращает снимок списка, чтобы внешним кодом нельзя было незаметно добавить объект мимо техосмотра.

### Что демонстрирует программа

Автоматическая демонстрация показывает успешную приёмку разных видов транспорта; принятие исправного, но сложного для новичка самоката; отказ неисправному, но удобному для новичка; добавление шлема и зарядной станции; отклонение повторного номера; количество транспорта и вещей; суммарное энергопотребление; список для новичков; имена и инвентарные номера всех объектов.

## SOLID: где и зачем

| Принцип | Реализация |
| --- | --- |
| **S — Single Responsibility** | `TransportBase` и `ThingBase` хранят свойства модели, `ServiceCenter` принимает решение о техосмотре, `FleetManager` ведёт парк, `Program.cs` занимается консольным взаимодействием. |
| **O — Open/Closed** | Новый транспорт можно сделать наследником `TransportBase`, при необходимости реализовав `IPowerConsumer`. Методы подсчёта и отбора в `FleetManager` менять не придётся. |
| **L — Liskov Substitution** | `Scooter`, `Bike`, `ElectricBike` используются как `ITransport`, без проверок их конкретного класса при приёмке и отборе. |
| **I — Interface Segregation** | `IInventoryItem` не требует энергопотребления, а `IPowerConsumer` добавляется только тем, кто расходует энергию. Шлем и обычный велосипед не имеют фиктивного расхода. |
| **D — Dependency Inversion** | `FleetManager` зависит от `IServiceCenter`, а не от `ServiceCenter`. Реализация выбирается в DI-контейнере в `VyshKat/Program.cs`. |

**Наиболее явно применён DIP:** `FleetManager(IServiceCenter serviceCenter)` позволяет менять техосмотр без изменения менеджера. Это демонстрируют `FakeServiceCenter` и тесты `FleetManagerTests`.

**Сознательно ограничен OCP:** при появлении нового типа транспорта в *интерактивном меню* потребуется добавить вариант в `ReadTransport` (`VyshKat/Program.cs`). Для трёх видов техники это проще и понятнее, чем строить фабрики/реестры только ради демонстрации. При этом `FleetManager` и его отчёты расширения не требуют. Это осознанный компромисс против overengineering.

## Что будет при расширении

- **Новый вид транспорта:** добавить класс-наследник `TransportBase`, реализовать `IPowerConsumer` только при наличии расхода; дописать вариант консольного ввода. `FleetManager`, отчёты и техосмотр менять не требуется.
- **Сотрудник эксплуатации:** создать отдельную модель и сервис учёта сотрудников; не реализовывать `IInventoryItem`, потому что сотрудники не ставятся на баланс.
- **Склад запчастей:** добавить новые виды вещей (если они инвентаризируются) или отдельный складской учёт. Существующий расчёт потребления и отбор транспорта для новичков менять не нужно.

## Какие тесты проверяют ключевые правила

- `FleetManagerTests.TryAddTransport_WhenInspectionAccepts_AddsTransport` и `TryAddTransport_WhenInspectionRejects_DoesNotChangeReports` — приёмка/отказ и эффект на отчёты.
- `FleetManagerTests.TryAddTransport_UsesInjectedServiceCenterInsteadOfRealOne` — подмена `IServiceCenter` тестовым `FakeServiceCenter`, без DI-контейнера в самом тесте (конструкторное внедрение зависимости).
- `FleetManagerTests.BeginnerReport_IncludesBoundarySixButExcludesFiveAndRejectedTransport` — граница правила `>= 6`.
- `ServiceCenterTests` — реальная логика учебного техосмотра, независимая от сложности управления.
- `DomainValidationTests` — некорректные значения; другие тесты `FleetManagerTests` — энергетика, уникальность номеров, инвентарный учёт и защита списка.

## Использование ИИ

Первоначальная структура проекта, базовые модели, DI-регистрация и первые четыре теста были представлены автором в исходном проекте. **ИИ использовался при проверке и доработке**: анализ требований, выявление смешения техосмотра с правилом для новичков, предложения по валидации и инвентарному учёту, переработка демонстрации, расширение тестов и подготовка документации.

Перед сдачей необходимо самостоятельно выполнить сборку и тесты на своей машине, проверить итоговое поведение и быть готовым объяснить изменения на защите. Здесь нет утверждения, что локальная проверка автором уже выполнена.
